# Separate free VM deployment — prepared, not deployed

The chosen plan is a separate VM. No public tunnel will be created from the user's Mac. No VM account, paid plan, instance, DNS record, certificate, or new public access has been created by this preparation.

## Capacity and architecture

The selected provider is AWS, using a new **Free account plan** only. See `AWS-checklist.md` before provisioning. No account plan upgrade, instance, storage, public IP, DNS or public route has been created by this package.

The minimum candidate is one `c7i-flex.large` (2 vCPU / 4 GiB), Ubuntu 24.04 LTS AMD64, with a 30 GB gp3 root volume at baseline settings. The installer remains provider-agnostic and also supports ARM64. The two Java heaps are capped at 512 MiB each; service memory caps total 3,028 MiB, leaving limited space for Ubuntu and Nginx. This is a low-concurrency reviewer fixture candidate, not a measured production capacity promise. The three real provider/native-adapter tests passed on the Mac; Linux installation, startup peak memory and reboot behavior remain untested. An 8 GiB `m7i-flex.large` offers more headroom, but consumes credits faster and is not selected automatically. The 1–2 GiB micro/small options are unsuitable for this combined deployment.

AWS explicitly lists both flex.large candidates as eligible for accounts created on or after 15 July 2025. Free account plans receive $100 initial credits, with up to another $100 earned through activities. The plan ends after six months **or credit exhaustion, whichever comes first**; six months of continuous server availability is not guaranteed. It does not charge until the owner upgrades to a Paid account plan. `AWS-pricing-example.json` contains dated official compute prices and clearly separates compute-only runway from additional charges. Oracle was investigated earlier but is not the selected provider.

## Installation

See `SSH-upload.md` for the direct private SCP upload/verification sequence. No public archive URL is needed.

1. User/operator completes the AWS Free account checklist and explicitly approves the selected eligible instance, or supplies another suitable free VM. Its publicIP/SSH route and permissions must be provided; there is no assumed cloud account.
2. Apply `cloud-init.yaml` when provisioning, or install prerequisites through `install.sh`. Cloud-init deliberately stops Nginx; it creates no public provider routes.
3. Verify the deployment bundle SHA256, upload and extract it into `/opt/honbako-review`. Do not upload the developer Mac's `runtime/` or its credentials. The bundle contains only code, current app query templates, original CBZs/cover, hashes and instructions.
4. Run `sudo bash /opt/honbako-review/Tools/reviewer-fixtures/vm/install.sh`. It supports Ubuntu24.04 only, downloads official pinned releases, verifies SHA256 before execution, generates new private credentials on the VM, creates4distinct non-login service users, and starts private loopback services.
5. Installer bootstraps restricted Komga/Kavita readers and imports only the original sample into real Suwayomi. The separate gateway gets only Suwayomi-specific credentials, not other provider administrator accounts. No upstream adminJWT/password/cookie is returned to a reviewer.
6. Run `sudo bash /opt/honbako-review/Tools/reviewer-fixtures/vm/verify-private.sh` after setup. It confirms loopback bindings and retries complete read-only probes while original CBZ scans finish. Probe proof is written privately under `/var/lib/honbako-review-setup`. It uses root-only `/etc/honbako-review/private-accounts.json` through the documented environment overrides. Do not paste it into terminal output/chat/source. The fixture bootstrap can be rerun; it does not delete unexpected content or other accounts.

Services generated by the installer: `honbako-komga`, `honbako-kavita`, `honbako-suwayomi`, `honbako-gateway`. Their systemd definitions live in `/etc/systemd/system/`; runtime state is split across `/var/lib/honbako-*`. Content roots contain only original review samples under `/srv/honbako-review`.

Pinned official native releases are in `releases-linux.json`: architecture-independent Komga/Suwayomi JARs; separate verified Kavita linux-arm64/linux-x64 archives. No macOS binary is packaged into this VM bundle. Python/Nginx/Java21 prerequisites come from Ubuntu's signed package repositories.

## Public activation is a separate explicit step

Proposed hostnames, not created here:

- `komga-review.honbako.xyz` → private39101
- `kavita-review.honbako.xyz` → private39102
- `suwayomi-review.honbako.xyz` → gateway39104

Never route Suwayomi's admin backend39103 or publish its credentials. VM/network firewall should allow only owner-scoped SSH and public80/443, with no direct provider ports. Keep SSH password login disabled; use the operator's existing approved key.

After the VM is confirmed free, installation passes, and public exposure is approved: point DNS-only A records at the dedicated VM, then run `activate.sh --reviewed-public-activation VM_PUBLIC_IPV4 CERTIFICATE_CONTACT_EMAIL` as root. It checks DNS, initially exposes only ACME/404, obtains free HTTPS certificates (subscriber terms remain interactive), then enables the bounded reverse-proxy routes. No wildcard DNS, credentials-in-URL, Mac tunnel, automatic paid upgrade, or owner MCP grant is used.

Finally, perform strict external TLS, unauthorized/wrong-password401, restricted reader catalog/chapter/page, restart-persistence, gateway-denial, and real iPhone-cellular tests. Publish only dedicated reader credentials into private App Store review information. Keep the VM available throughout review and retain original fixtures/provenance. Remote readiness is not established until these checks pass.

MCP remains on Honbako's existing hosted service with verified Apple Sandbox/Production separation. A reviewer must obtain their own genuine test entitlement and authorize their own OAuth connection/workspace; no server grant, Xcode receipt, owner's token, or entitlement bypass is included.

The Linux installer pre-seeds five email templates from a pinned official KavitaEmail commit, with SHA256 verification, before starting Kavita. This avoids its first-run migration requiring Internet access inside the loopback-only runtime. Kavita config and its mutable web-root copy remain in its isolated state directory.
